# 外部插件用清单加载，进程内模块编译期组装

**Status**: superseded by [ADR-0027](0027-mcp-is-a-tool-source-not-a-plugin-host.md) (2026-10-23)；原实现里程碑 M5
**修订**: 2026-10-23 M5 范围——清单枚举移除 `CustomStdio`，M5 只实现 MCP 传输；`Acp` 保持识别但不支持。插件分发仍归 host/生态。
**来源**: [#16](https://github.com/zibyn/asterpath/issues/16)

## Context

[#2](https://github.com/zibyn/asterpath/issues/2) 已经把模块分成两类：进程内模块随宿主编译、由组装根显式构造；外部插件经子进程或 MCP 接入，由进程内 adapter 暴露为同一批能力 trait。v1 明确不做动态发现与热替换。

剩下的问题是外部插件的启动契约：清单长什么样、谁提供、如何做版本协商、工具如何命名、加载失败是否拖垮宿主。没有这层约定，每个 adapter 会发明自己的配置格式与冲突策略，宿主无法在启动前判断一个插件能不能用。

## Decision

- **只有外部插件有清单**。进程内模块没有 manifest，由 Cargo 依赖与组装根选择；"可选模块" = 独立 crate，不是运行期开关。
- **框架定义形状，host 提供数据**。`PluginManifest` 是 `asterpath-plugin-host` 的类型；框架不读文件、不做发现、不展开环境变量、不持久化清单。
- **命名空间强制**。外部工具以 `<plugin_id>__<tool_name>` 暴露；`__` 保留；任何名称非法、超长或碰撞都使整插件加载失败，不做部分注册、不 last-write-wins。
- **版本协商是精确白名单**。`protocol_versions` 列出接受的协议版本；握手结果必须命中；插件自身版本只用于诊断；不降级、不回退。
- **失败按插件隔离**。可选插件失败不阻止宿主启动；`required: true` 的插件失败中止启动；失败插件不贡献任何工具。
- **没有热替换**。升级 = 重启进程；运行中的会话靠日志恢复；v1 不记录工具实现指纹，同名工具升级时必须由插件保持 replay 语义或声明为 `Unsafe`。
- **秘密不落日志**。manifest 的 `env` 等敏感字段 `Debug` 脱敏，清单不进入事件日志。

## Consequences

- 宿主在启动前就能校验清单，插件失败边界清晰；模型永远看不到半可用的插件。
- 一个坏工具名可以让整个插件不可用；这是为"没有部分状态"付的代价，插件作者必须在发布前自检名称。
- 协议版本只能是精确匹配；旧版插件不会因为"看起来兼容"被放行，宿主需要显式更新白名单。
- 升级需要重启；崩溃后、升级前的 `Safe` 工具重跑语义靠宿主/插件契约保证，框架不强制。
- `ToolCallRequested` 需要能记录"工具不存在"：`Provenance` 增加 `Unknown`，`replay` 取保守的 `Unsafe`；恢复时据此写 `Failed{NotFound}`。
- 清单形状变化需要提升 `manifest_version`，与日志 schema 版本互不影响。

## Considered alternatives

- **动态发现 / 热替换**：更灵活，但违反 #2 的生命周期与恢复模型，且运行期替换会让在途调用与恢复语义不可判定。
- **feature-gated 单体**：编译期裁剪，但模块会编译进彼此，替换仍需改内核；ADR-0001 已拒绝。
- **部分工具注册**：插件能"尽量可用"，但宿主与模型会面对不确定的能力集，恢复与重试也失去明确边界。
- **协议版本用 semver 范围**：MCP 版本是日期字符串，不是 semver；发明范围语义只会制造误判。精确白名单更诚实。
- **在 `ToolCallRequested` 记录实现指纹**：恢复更强，但改变日志 schema 与 #3/#7 的恢复路径；v1 把"升级保持 replay 语义"留给宿主/插件契约。
- **把清单放进 protocol crate**：清单是 host 启动配置，不是跨模块能力契约；放在插件宿主模块里，等 #15 收敛打包位置。
