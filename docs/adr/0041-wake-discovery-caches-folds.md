# 唤醒发现以唤醒缓存保存折叠结果，判定仍只来自折叠

**Status**: rejected (2026-10-25) by [ADR-0047](0047-multi-user-and-multi-node-belong-to-the-platform.md)：多机部署归集成平台
**部分修订**: [ADR-0023](0023-storage-holds-log-and-catalog-wake-by-fold.md) 的「存储契约不物化派生状态」
**来源**: [#148](https://github.com/zibyn/asterpath/issues/148)
**调研**: [multi-process-storage-audit.md](../research/multi-process-storage-audit.md)（E9）

## Context

ADR-0023 让 `wakeable()` 每次折叠全部会话的日志，并约定出现实测瓶颈时再加索引。web 部署是单进程上千会话、滚动重启，冷启动全量折叠的成本可以预见，不必等实测。

直接让后端维护「有未闭合意图」索引行不通：后端只看得到事件种类，看不到类型化内容；意图要按 id 配对才知道是否闭合，待处理输入与悬空压缩另有规则。让后端解码事件，会把同一套唤醒规则在每个后端重写一遍，这正是 ADR-0023 删掉三张派生表的原因。

## Decision

- **唤醒缓存**：引擎折叠一个会话后，把「折叠到的 log id、当时是否需要唤醒」写回存储。会话的 frontier 超过该 log id 即失效。
- **判定仍只来自折叠**：发现唤醒时，只重新折叠缓存为需要唤醒、已失效或缺失的会话；缓存为不需要唤醒且仍有效的会话跳过。唤醒缓存可以丢弃，不是真相源。
- **后端不解释事件**：唤醒缓存由引擎算出，后端只存取并按 frontier 判断候选。
- **任何进程都可写，不受属主纪元约束**：过期的缓存自然失效，最坏只多折叠一次；后端只保留 log id 更大的一份。写入时机是唤醒发现折叠之后，以及属主驱动结束、会话空闲时。
- **可选能力**：契约新增「列出候选」与「写缓存」，默认实现分别返回全部会话、忽略写入；不支持的后端退回全量折叠，结果相同。唤醒缓存不进目录项，宿主看不到。
- **只用于唤醒发现**：退役与打开会话时的事实仍从完整折叠得到。

## Consequences

- 冷启动只折叠需要唤醒或最近有写入的会话；空闲会话的成本降到一次候选查询。
- 第三个存储后端仍只需能追加、扫描、列会话；实现唤醒缓存是优化。
- 退役必须一并删除唤醒缓存。
- 已有的库没有唤醒缓存，第一次唤醒发现仍是全量折叠。
- 与 [ADR-0036](0036-per-session-tree-ownership.md) 交汇：被别的进程持有的会话树在折叠前排除。

## Considered alternatives

- **后端在 append 事务里维护未闭合意图索引**：后端要理解事件语义，每个后端各写一份配对规则。
- **引擎每次 append 附带「写完后是否需要唤醒」**：非属主写入（用户输入、审批）的进程手上没有最新会话事实。
- **只在进程内缓存折叠结果**：省不了冷启动，而冷启动是滚动重启的常态。
