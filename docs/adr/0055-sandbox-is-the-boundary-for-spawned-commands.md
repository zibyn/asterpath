# 起进程的工具以沙箱为边界，审批只问能否越出沙箱

**Status**: accepted (2026-10-26)；「模式切换立即生效；启动进程时总按当前模式收紧」与否决「按回合快照模式」的理由部分取代 by [ADR-0056](0056-read-only-cap-sticks-to-the-calls-it-allowed.md)（因只读上限而放行的调用保留上限）
**来源**: [#193](https://github.com/zibyn/asterpath/issues/193)、[#194](https://github.com/zibyn/asterpath/issues/194)
**相关**: [ADR-0007](0007-approval-and-sandbox-layers.md)、[ADR-0019](0019-sandbox-seam-and-policy.md)、[ADR-0037](0037-session-environment.md)

## Context

参考应用的审批策略只看工具声明的副作用等级。`bash` 声明为变更，所以「询问」模式下每条命令都要问，「只读」模式下连 `ls` 都被拒绝，即使它本来就在只读沙箱里执行。沙箱已经能强制「不能写」，审批却仍把每条命令当成无约束的写操作。

另一种做法是按命令文本判断只读，给 `ls`、`find` 开白名单。命令文本很难判断准：`find -delete`、仓库配置让 `git` 执行 helper、glob 展开出危险参数。Codex 因此删除了它的安全命令白名单，只靠沙箱；Claude Code 保留一组内置只读命令，再叠加用户可配置的允许 / 询问 / 拒绝规则。

ADR-0007 与 ADR-0019 规定审批与沙箱正交、策略归应用、框架不读沙箱状态。这里的决定都在应用的审批策略里，不改变那两条。

## Decision

- **对起进程的工具，沙箱是主要边界**：调用会在受限沙箱（`ReadOnly` / `WorkspaceWrite`）里执行时，应用的审批策略默认允许。审批只回答「能否在沙箱之外执行」：没有可用后端、有效策略为 `FullAccess`。进程内工具没有沙箱，按「沙箱外」处理。
- **审批模式只收紧，不放宽**：每个审批模式是「沙箱外调用的结论 + 沙箱策略上限」。只读模式把沙箱收紧到 `ReadOnly`，沙箱外拒绝；询问模式沿用配置的沙箱，沙箱外询问；放行模式沿用配置的沙箱，沙箱外允许。模式切换立即生效；启动进程时总按当前模式收紧，结果只会更严。
- **命令规则只改审批结论**：允许 / 询问 / 拒绝规则按工具名匹配，shell 工具还可以按命令前缀匹配；复合命令拆成子命令，全部命中允许才算允许，解析不了就不算命中。拒绝优先于询问，询问优先于允许。规则不改变沙箱策略。另有一组不可修改的内置只读命令作为允许规则，只在沙箱外起作用。
- **没有可用后端时明确降为 `FullAccess`**：应用启动时检测后端；不可用就把有效策略设为 `FullAccess` 并显示「无沙箱」，于是每次调用都按「沙箱外」得到审批结论。这是应用的明确选择，不是缺后端时的静默降级，ADR-0019 的 fail closed 不变。
- **内核只补一个上下文字段**：`ToolContext` 带上根会话，与审批请求对齐，让应用的工具在执行时找到会话树的审批模式。逐次调用的策略由应用写进 `ctx.spawn.sandbox`，内核不新增策略钩子。

## Consequences

- 有沙箱时，「询问」模式下的 shell 命令不再逐条询问；有网络副作用的命令（如 `git push`）要靠询问或拒绝规则拦住，因为文件系统沙箱不管网络。
- 只读模式下 `/tmp` 不可写，需要临时文件的命令会自己报错。
- MCP stdio 服务在加载时按配置的沙箱启动，审批模式收紧不到它们，MCP 工具只能靠审批与规则约束。
- 没有沙箱的平台上，询问模式与现在一样逐条询问，放行模式不加沙箱直接执行。
- 仍不做越出沙箱的请求（ADR-0019）；被沙箱挡住的命令把失败返回给模型。

## Considered alternatives

- **审批只看副作用等级（现状）**：沙箱已强制的约束仍逐条询问，只读模式下 shell 不可用。
- **只按命令文本判断、不靠沙箱**：判断不准，失败方向是放行；pi 的正则白名单会放过 `find . -delete`。
- **审批结论携带收紧后的沙箱策略**：把「能不能做」和「隔离到什么程度」重新绑进一个内核类型，ADR-0007 已否决合并两层。
- **按回合快照模式**：在模式只收紧的前提下，立即生效不会让本该询问的调用被放行，快照只增加状态。
