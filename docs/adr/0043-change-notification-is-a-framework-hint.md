# 变更通知是框架提供的提示：每进程一个轮询器，宿主可接入变更总线

**Status**: proposed (2026-10-25)
**来源**: [#160](https://github.com/zibyn/asterpath/issues/160)（拆自 [#155](https://github.com/zibyn/asterpath/issues/155)）
**相关**: [ADR-0036](0036-per-session-tree-ownership.md)、[ADR-0038](0038-watch-separates-observing-from-driving.md)、[ADR-0042](0042-approval-asks-are-logged.md)

## Context

多进程共用存储后，属主要发现别的进程写入的审批决定与取消请求，观察者要看到属主提交的新记录，非属主节点要看到新的询问。各处各自按会话轮询，查询次数是「会话数 × 等待点」，延迟与数据库负载都随会话数增长。

存储只当作数据持久化层（ADR-0036），不能用 `LISTEN/NOTIFY` 之类的后端特性推送。

## Decision

- **通知只是提示**：内容是「会话 X 提交到了 log id Y」。可以丢失、合并、乱序；消费方收到后一律按自己的游标重读日志，另有较长间隔的兜底轮询。
- **框架在每个进程内跑一个轮询器**：存储契约只加一个可选的纯数据查询——「某游标之后有哪些会话有新记录」；轮询器把结果扇出给本进程内的等待方与观察者。提交顺序与 log id 分配顺序不一致的后端，靠回看窗口与兜底轮询补齐。不支持该查询的后端退回按会话轮询 frontier。
- **变更总线是可选的宿主适配器**：框架定义接口，提交后发布、各进程订阅，收到的同样只是提示。传输由宿主提供（Redis、NATS、节点间 HTTP，或宿主自己用的数据库通知），不属于存储契约。
- **一处机制**：等待审批、等待取消请求、观察、待审批可见，都由同一个「会话有变化」机制唤醒，不各自轮询。同进程内的写入仍立即唤醒。

轮询与兜底间隔、回看窗口大小见 storage.md。

## Consequences

- 每个进程每个间隔只查一次存储，与会话数无关。
- 不接变更总线时，跨进程延迟的下限是轮询间隔。
- 第三个存储后端仍只需能追加、扫描、列会话；实现游标查询是优化。

## Considered alternatives

- **用后端原生推送**（Postgres `LISTEN/NOTIFY`、SQLite `data_version`）：语义随后端变化，把协调押在数据库特性上。
- **按会话或按会话树订阅**：每个后端要维护大量订阅，观察者也不一定是属主。
- **框架自带节点间传输**：内核要长出服务发现与网络配置，越出可嵌入库的边界。
