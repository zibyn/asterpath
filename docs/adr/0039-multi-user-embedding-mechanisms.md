# 多用户内嵌：用户是宿主元数据，内核只补按会话的机制

**Status**: accepted (2026-10-25)；Context 前提（单进程上千用户是平台的形态，不是内核目标） 部分取代 by [ADR-0047](0047-multi-user-and-multi-node-belong-to-the-platform.md)
**调研**: [design-audit-2026-10-25.md](../research/design-audit-2026-10-25.md)、[kernel-host-boundary-audit.md](../research/kernel-host-boundary-audit.md)

## Context

web 以库方式内嵌内核，单进程服务上千用户。内核没有用户维度：会话目录只能按父会话过滤；provider 请求不带会话，宿主无法按用户选凭据；审批端点按进程计数，只要进程里有一个端点在线，其他无人值守会话遇到需审批的调用就会挂起而不是拒绝。

参考产品都没有用户身份：opencode 只有一个服务口令，多租户靠部署单元隔离；Codex、Claude Code、pi 是单用户工具。

## Decision

- **内核里没有「用户」概念**：租户或用户标识由宿主写进会话元数据（ADR-0032）；认证与授权在宿主。
- **会话目录可按元数据过滤**。
- **provider 请求携带会话上下文**（会话 id 与宿主元数据），宿主的 provider 包装可据此选择凭据或端点。
- **审批端点按会话树注册**：某会话树没有在线端点时，需审批的调用按无端点处理（拒绝），不受同进程其他会话树的端点影响。

## Consequences

- 一个进程里的会话可以属于不同用户，互不可见与否由宿主的查询和授权决定，内核不保证隔离。
- 审批端点的注册从进程级改为会话树级，现有宿主要随之改。
- 元数据过滤需要存储后端支持，按键值等值匹配即可。

## Considered alternatives

- **内核内建用户与权限表**：把策略放进内核；参考产品也都不做。
- **每用户一个 `Asterpath`**：存储与调度被切成多份，上千用户时实例无限增长。
- **按用户分库**：跨用户的运维与唤醒发现都要宿主自己拼。
